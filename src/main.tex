\chapter{Introduction}
\label{ch:introduction}
Modern software is often written in such a way that it is event-driven, or in other
words, reactive. This means that applications reacts to an incoming event
by creating subsequent events that arise as a reaction to the incoming event.
Such an application is often called a reactive system. Reactive systems are
often implemented with callbacks or by implementing the Observer Pattern.
However, this does not come without its drawbacks as this may lead to
\enquote{inversion of control} or \enquote{callback
	hell}\cite{surveyRP2024, bainomugisha2013survey}. To alleviate this we
introduce \textbf{Reactive Programming}. A programming paradigm that allows the
user to write reactive systems in a declarative way. Traditionally the sum and
the product of
two elements would be written as shown in Listing~\ref{lst:imperative-product-sum}.
\par
\begin{listing}[htbp]
	\begin{lstlisting}[language=C]
int x = 5;
int y = 10;
int s = x + y;
int p = x * y;
// x changes state
x = 10;
// s requires recomputation
s = x + y;
// p requires recomputation
p = x * y;
    \end{lstlisting}
	\caption{Imperative product and sum}
	\label{lst:imperative-product-sum}
\end{listing}
Whenever $x$ or $y$ would change state, you would have to manually update
$s$ and $p$. Reactive Programming allows you to declare $x$ and $y$ as sources of data
and $s$ and $p$ as the result of the relevant computations.
Whenever the value of $x$ or $y$ would change, the variables
dependent on the sources would be automatically recomputed, and the result
propagated further in the reactive system. Schematically the dependency graph of product-sum would look
like Figure~\ref{fig:dependency-graph-product-sum}
\begin{figure}[ht]
	\centering
	\includegraphics[scale=0.7]{./images/product-sum-graph.drawio.pdf}
	\caption{Dependency graph for product-sum}
	\label{fig:dependency-graph-product-sum}
\end{figure}

\section{Contributions}
\label{sec:contributions}
Reactive Programming is used across a multitude of domains. It is used in web
and mobile development for instance. However, we will be focussing on using it
for the Internet of Things (IoT). IoT consists of multiple physical objects,
usually with very limited computing power and/or memory. In this thesis we
introduce a way of declaring a reactive program across multiple devices from a
single source. This means that the developer declares the program once, along
with declarations where which part of the program lives and then deploys the
program to the relevant devices making use of ROS.
This is achieved by the following components:
\begin{itemize}

	\item An extension of the Remus VM~\cite{oeyen2024virtual}, more
	      specifically, extending the language to accept a declaration of where
	      which part of the program lives. The Remus compiler will use this
	      metadata to split the Haai reactor declarations into an embedded part
	      and a server part. Each piece will then be available for the user to
	      be deployed in their respective parts of the IoT network.
	\item A new tool called CHaai, which translates the Remus bytecode
	      obtained from compiling the Haai program into a C program. The C
	      program will be required to run the program on microcontrollers using ROS.
	\item A C port of the existing Remus VM written in rust~\cite{descheemaeker2023compilation}, also created to allow developers to create reactive
	      programs for microcontrollers. However, it is adapted with respects to
	      the current Instruction Set Architecture (ISA) of the Racket version
	      of Remus~\cite{oeyen2024virtual} and allows usage of ROS.
\end{itemize}

\chapter{State of the Art}
\label{ch:state-of-the-art}
Many programs spend most of their time reacting to events or their environment:
a thermostat displays the temperature a sensor picks up, a lightbulb reacts to
the pressing of a button, a notification is pushed once an email arrives.
Reactive Programming (RP) is a programming paradigm that suits these kinds of
programs. Instead of writing code that explicitly updates values when something
changes, the programmer declares how values depend on one another and the
language takes care of propagating changes through those
dependencies~\cite{surveyRP2024}.
\par
Embedded devices are prime examples of devices that spend their lifecycle
reacting to their surroundings, often taking part in a much larger system.
Consider, for instance, a modern-day car, which is equipped with a myriad of
subsystems. A braking system reacts to an obstacle drawing too close to the
front of the car while a dashboard behind the steering wheel reacts to the
metrics fed by other subsystems such as temperature, speed, gear shift,
etc\dots. All these subsystems communicate with each other and depend on one
another to form a much larger, coherent system. Inherently, these systems are
distributed as they span multiple devices. Robots are no different: their
sensors, actuators and controllers often run on separate boards that must also
cooperate.
\par
Programming such a system is not trivial. Each device runs its own program,
written for its hardware. Additionally, the developer has to connect these
devices through a medium that allows them to communicate with each other. While
it is possible to write reactive programs for all these devices and then glue
them manually, doing so is cumbersome~\cite{surveyRP2024,
weisenburger2018scalaloci}. Creating a single RP program and avoiding this
manual glue is the challenge of this dissertation. Moreover, we want to build on
an existing robotics framework, so that its software tools and libraries can aid
the development of future robotics software. The motivation behind choosing RP
as our paradigm is given together with the necessary background in
\cref{sec:reactive-programming}.
\par
The following requirements arise. First, we need to choose an RP language that
runs on microcontrollers (MCUs). This is discussed in
\cref{sec:rp-languages-targeting-mcus}. Second, we need a robotics framework
that has an SDK and a user base, and runs on MCUs. Preferably, it also abstracts
away the communication between devices, independent of the medium used (e.g.\
UART, Bluetooth). This is discussed in \cref{sec:robotics-frameworks}. Third,
the robotics framework has to work together with the RP language. This is
discussed in \cref{sec:revisiting-the-problem-statement}.
\section{Reactive Programming}
\label{sec:reactive-programming}
Software nowadays is largely event-driven, meaning that programs spend most of
their time reacting to incoming data. In imperative languages this is
traditionally implemented with handlers, callbacks or the Observer pattern. The
programmer registers a function with an event source and the runtime calls that
function when that event occurs~\cite{surveyRP2024}.
\par
Unfortunately, this scales poorly as it gives rise to two problems: callback
hell and inversion of control~\cite{surveyRP2024}. Callback hell occurs when
callbacks are so deeply nested that it becomes difficult to tell what each
callback does and when it is invoked. An example is shown in
\cref{lst:illustration-of-callback-hell-in-javascript}, where a temperature
sensor reads its pin, normalizes the read voltage into temperature and displays
it on a screen. Any errors while displaying or sending are logged.
\begin{listing}[ht]
    \centering
	\begin{lstlisting}[language=JavaScript]
readSensor((voltage) => {
    normalize(voltage, (temperature) => {
        display(temperature, (errors) => {
            log(errors, () => {
                sendToServer(temperature, (errors) => {
                    log(errors, () => {
                        // etc...
                    })
                })
            })
        })
    })
})\end{lstlisting}
	\caption{Illustration of callback hell in JavaScript}
	\label{lst:illustration-of-callback-hell-in-javascript}
\end{listing}
\par
Inversion of control is related to callbacks: instead of the programmer's code
being in charge, the programmer hands the function to a framework or event
source and the framework decides when it is called. As a result, the control
flow is no longer visible in the program text as the framework decides how and
when the programmer's code is run. In \cref{lst:inversion-of-control-python} we
define two functions \texttt{hello} and \texttt{foo} within the Flask web
framework. These functions are registered to be called when their respective
endpoints \texttt{"/hello"} and \texttt{"/foo"} are requested. The programmer
never calls them directly. Additionally, the flow between receiving the request
and the registered function being called is hidden inside the framework.
\begin{listing}[ht]
	\centering
		\begin{lstlisting}[language=Python]
@app.route("/hello")
def hello():
    return "world"

@app.route("/foo")
def foo():
    return "bar"\end{lstlisting}
		\caption{Inversion of control in Python, using the Flask web
			framework}
		\label{lst:inversion-of-control-python}
\end{listing}
\par
Reactive Programming (RP) attempts to solve these problems~\cite{surveyRP2024}.
RP is a declarative programming paradigm that allows the developer to declare a
program in terms of dependencies, instead of having to manually manage these
dependencies~\cite{surveyRP2024}. A value that is computed from other values is
said to be dependent on them. When these values in turn also have other values
that they depend on, they form a dependency chain. In an imperative language,
you would have to manually update all these values in the correct order. In RP,
the actual propagation of the state change in the dependency chain is abstracted
away in the language design. For instance, in a program you could have two
variables \texttt{x} and \texttt{y} that hold values and variable \texttt{s}
which holds the sum of \texttt{x} and \texttt{y}. Under the imperative paradigm,
whenever \texttt{x} or \texttt{y} would change state, it would require manual
recomputation of \texttt{s} as shown in
\cref{lst:manual-recomputation-of-s-a-dependent-on-x}.
\begin{listing}[ht]
	\begin{lstlisting}[language=C]
int x = 5;
int y = 10;
int s = x + y;
printf("%d", s); // 15
x = 10; // state change
printf("%d", s); // 15
// requires manual recomputation of s
s = x + y;
printf("%d", s); // 20
\end{lstlisting}
    \caption{Manual recomputation of \texttt{s} in C}
	\label{lst:manual-recomputation-of-s-a-dependent-on-x}
\end{listing}
\par
In Reactive Programming, it is sufficient to update either \texttt{x} or
\texttt{y} and the change is propagated throughout the dependency chain. A
dependency chain can also be seen as a directed acyclic graph (DAG), with input
variables and output variables, often called \emph{signals}~\cite{surveyRP2024}.
Converting \cref{lst:manual-recomputation-of-s-a-dependent-on-x} into a DAG
yields the graph shown in \cref{fig:dag-for-automatic-sum}. In
\cref{lst:manual-recomputation-of-s-a-dependent-on-x}, the programmer has to
maintain these dependencies manually; in RP, the language does so automatically.
In essence, whenever an input signal changes state, the change is propagated
through the graph and finally updates its output signals. An example in the
reactive language REScala is shown in
\cref{lst:automatic-recomputation-of-s-a-dependent-on-x}. The input signals
\texttt{x} and \texttt{y} are declared using the \texttt{Var} class and the
dependent signals can be derived with \texttt{Signal \{ \dots \}}, as seen in
the example with \texttt{sum}. In this example we can see that \texttt{s} is
declared once through the \texttt{Signal} dependency, instead of nested
callbacks. Whilst RP does not fully solve inversion of control, since the
runtime still decides when it is called, it does make the data flow
explicit~\cite{Larsen2021}.
\begin{figure}[ht]
    \centering
    \includegraphics{./images/sum-dag.drawio.pdf}
    \caption{Dependency graph for \texttt{x}, \texttt{y} and \texttt{s}}
    \label{fig:dag-for-automatic-sum}
\end{figure}
\begin{listing}[ht]
	\begin{lstlisting}[language=REScala]
def sum(a: Signal[Int], b: Signal[Int]): Signal[Int] = Signal { a.value + b.value}

@main def demo(): Unit =
    val x = Var(5)
    val y = Var(10)
    val s = sum(x, y)

    println(s"s = ${s.now}") // s = 15
    x.set(10)
    println(s"s = ${s.now}") // s = 20

\end{lstlisting}
    \caption{Automatic recomputation of \texttt{s} in REScala}
	\label{lst:automatic-recomputation-of-s-a-dependent-on-x}
\end{listing}

\subsection{Hosted and independent reactive languages}
\label{sec:hosted-and-independent-reactive-languages}
In practice there are two kinds of reactive languages. The first kind are
\emph{hosted} reactive languages, which are built on top of an existing host
language. Examples are REScala, built on top of Scala, and Yampa, built on top
of Haskell. These RP languages inherit the tools of their host language such as
compilers, runtime, and libraries~\cite{surveyRP2024}. These reactive languages
consist of two parts: a reactive part and a non-reactive part of the code. The
reactive part is the part that the host language is extended with. The
non-reactive part is functions or code of the host language that work on signals
through a mechanism called \emph{lifting}. However, lifting has two drawbacks.
First, it can lead to \emph{reactive thread hijacking}: the runtime has to wait
for the lifted function to return, so a function that never returns takes over
the runtime and makes the program unresponsive. Second, lifting can cause a
\emph{reactive/imperative impedance mismatch}: the runtime, not the programmer,
decides the order in which the lifted functions run, so side effects such as I/O
may happen in an unintended order and lead to faulty
behaviour~\cite{oeyen2024reactive}.


The second kind are \emph{independent} reactive languages. These languages were
built from the ground up with their own compilers, runtime, tooling, etc. Some
examples are Haai, EmFRP, CFRP and Elm~\cite{surveyRP2024}. This does not mean
that they avoid lifting, since some of these languages still use a non-reactive
part to feature data structures and functions within the reactive
part~\cite{surveyRP2024}. An independent reactive language lacks the ecosystem
of a host language, and reusing existing code requires a foreign function
interface. In return, its designers control the entire implementation, so they
can enforce the properties their target domain needs, such as safety and
efficiency~\cite{surveyRP2024}.

An extreme case is \emph{Haai}, a pure reactive programming language, which has
no non-reactive parts~\cite{oeyen2024reactive}. In Haai a reactor is the only
computational unit, which is essentially a description of the DAG shown in
\cref{fig:dag-for-automatic-sum}. Instantiating a reactor is called a
\emph{deployment}, which supplies the reactor with its concrete input signals,
called \emph{sources}, and creates its output signals, called
\emph{sinks}~\cite{oeyen2024reactive}. The benefit of Haai is that everything is
a reactor; even primitives such as \texttt{+} and \texttt{-} are reactors, and
not functions. This means that there is no lifting and consequently Haai does
not suffer from the drawbacks of lifting (thread hijacking and impedance
mismatch)~\cite{oeyen2024reactive}. An example of a Haai program can be seen in
\cref{lst:reactive-program-in-haai}. \texttt{defr} is used to declare a reactor
along with its name and its sources \texttt{x} and \texttt{y}. \texttt{def} is
used to define internal signals and \texttt{out} is used to declare one or
multiple sinks, though if there is only one sink, ending the reactor with it is
sufficient instead of using \texttt{out}~\cite{oeyen2024reactive}. In
\cref{lst:reactive-program-in-haai} we define \texttt{s} as an internal signal,
which is the result of the deployment of the \texttt{+} reactor. The signal
\texttt{time} is a built-in signal that increases its value over time. Should
the values of the sources \texttt{x} or \texttt{y} change, the change is
automatically propagated to the deployment of the \texttt{+} reactor and to the
sink \texttt{s}. In the case of \texttt{total}, which is the result of the
deployment of the \texttt{sum} reactor with the sources \texttt{time} and
\texttt{10}, the sum is recomputed each time the value of the \texttt{time}
signal changes.
\begin{listing}[ht]
	\begin{lstlisting}[language=haai]
(defr (sum x y)
    (def s (+ x y))
    (out s))

(def total (sum time 10))
;; total = 10, 11, 12, ...\end{lstlisting}
	\caption{Reactive program in Haai}
	\label{lst:reactive-program-in-haai}
\end{listing}
\section{RP languages targeting MCUs}
\label{sec:rp-languages-targeting-mcus}
Reactive Programming (RP) has many uses, from web applications that react to the
input of users to microcontrollers (MCUs), which react to signals from
hardware~\cite{surveyRP2024, rpbaremetal2022}. In this thesis we focus on RP for
MCUs, which are used in a growing number of domains, such as the Internet of
Things (IoT)~\cite{gubbi2013internet}, edge computing~\cite{shi2016edge} and
artificial intelligence (AI)~\cite{liu2023space}.
\par
MCUs have little memory and processing power, and support few programming
languages, mostly low-level ones such as C, C++ and Rust~\cite{sharma2024rust}.
This is also why it is hard to use hosted reactive languages on these devices:
they often rely on the runtime of their host language~\cite{surveyRP2024,
oeyen2024virtual}. For instance, Yampa, a language built on top of Haskell,
cannot be used on most MCUs because the Haskell runtime is too large to be
flashed onto them~\cite{sawada2016emfrp}. Despite this, there have been efforts
to get reactive languages running on MCUs.
\par
To compare these languages, we use the following requirements:
\begin{itemize}
    \item \emph{Predictable memory footprint}: the program's memory usage must
        be known in advance to ensure it meets the memory constraints of the
        MCU.
    \item \emph{Access to sensors and actuators}: the program must be able to
        read sensors and drive actuators, either through the language itself or
        through MCU-compatible code.
    \item \emph{Interoperability}: the reactive language must be able to
        interoperate with a low-level language that the robotics framework is
        written in.
    \item \emph{Portability}: the reactive program must be able to run on
        different MCUs within a system, or robot.
\end{itemize}
\cref{tab:rp-languages-for-mcus} gives a high-level overview of independent RP
languages that were designed to run on MCUs, and whether they meet the
requirements above.
\par
Some honourable mentions that fell just short of
\cref{tab:rp-languages-for-mcus} are Hailstorm, ReactiFi and RT-FRP. Hailstorm
runs on top of the Erlang virtual machine, which occupies about 30\,MB of
memory~\cite{sarkar2020hailstorm}. Like the Haskell runtime, this exceeds the
memory of most MCUs. Additionally, running Hailstorm on MCUs was left as future
work, and in the presence of recursion its memory usage cannot be predicted
statically~\cite{sarkar2020hailstorm}. ReactiFi specifically targets Wi-Fi
chips~\cite{sterz2021reactifi, descheemaeker2023compilation}, so unlike the
other languages in \cref{tab:rp-languages-for-mcus}, it is not a general-purpose
language for MCUs. RT-FRP statically bounds the time and memory of each
execution step~\cite{wan2001rtfrp}, but its focus is on the formal integration
with a base language rather than on implementing the language. Its successor
E-FRP, which is included in the table, shifts the focus to implementation and
was compiled to run on an MCU~\cite{wan2002efrp}.
\par

As \cref{tab:rp-languages-for-mcus} shows, none of these languages meets all the
requirements. However, some requirements, such as interoperability, can be met
by building additional tooling. Juniper has no predictable memory
footprint~\cite{helbling2016juniper}, so we leave it out. E-FRP has a similar
design to EmFRP~\cite{rpbaremetal2022}, but it is a prototype that generates C
for the compiler of one specific MCU, the PIC16C66~\cite{wan2002efrp}. EmFRP, in
contrast, generates platform-independent ANSI C that can run on multiple MCUs,
and offers more language features, such as modules, algebraic data types and
type inference~\cite{sawada2016emfrp}. Therefore, we compare the following
languages: EmFRP, CFRP and Haai + Remus.
\subsection{EmFRP}
\label{sec:emfrp}
EmFRP is a reactive language designed to work on small-scale embedded systems
that cannot run a full-fledged operating system such as
Linux~\cite{sawada2016emfrp}. EmFRP works as follows: the developer declares a
series of nodes, which can be seen as signals. These nodes can refer to other
nodes, which defines the dependencies between nodes. These connected nodes form
a directed graph. EmFRP does not allow recursion; instead, EmFRP allows cycles
through the \texttt{@last} annotation, which allows referring to the previous
value of any node~\cite{sawada2016emfrp}. Restricting recursion allows
determining the memory footprint at compile time~\cite{sawada2016emfrp}.
\par
EmFRP's prototypical example is a thermostat, shown in
\cref{lst:thermostat-controller-emfrp}. We start by declaring the module name,
the program's inputs, in this case the sensed temperature and the periodical
pulse, and the outputs, in this case the heater state (on/off), followed by the
used libraries. Afterwards, a single node is declared that periodically turns
the heater on if the temperature is below 50 and off otherwise. Between pulses,
the heater keeps its state~\cite{sawada2016emfrp}.
\begin{listing}[ht]
	\begin{lstlisting}[language=emfrp]
module Thermostat
in
    temperature : Int,  # temp sensor
    pulse1min : Bool    # periodical pulse
out
    switching : Bool    # heater state
use
    Std                 # standard library

node init [ False ] switching =
    if pulse1min then
        temperature < 50
    else
        switching@last  # previous value\end{lstlisting}
	\caption{Thermostat controller in EmFRP~\cite{sawada2016emfrp}}
	\label{lst:thermostat-controller-emfrp}
\end{listing}
\par
EmFRP's example does give rise to the question of how peripherals are connected.
EmFRP's compiler compiles the EmFRP program into two C files: on the one hand it
generates FRP C code and on the other hand an I/O code skeleton, shown in
\cref{lst:io-code-skeleton-for-thermostat}. The developer is required to fill in
the I/O skeleton with the platform- and/or hardware-dependent code so the FRP
code can interact with the hardware~\cite{sawada2016emfrp}. After the I/O code
is filled in, the developer can use a C compiler targeting the platform to get
the appropriate binary~\cite{sawada2016emfrp}.
\begin{listing}[ht]
	\begin{lstlisting}[language=c]
#include "Thermostat.h"
void Input(int *temperature, int *pulse1min){
    /* Your code goes here ... */
}

void Output(int *switching){
    /* Your code goes here ... */
}

int main(){
    ActivateThermostat();
}\end{lstlisting}
	\caption{I/O Code Skeleton for Thermostat~\cite{sawada2016emfrp}}
	\label{lst:io-code-skeleton-for-thermostat}
\end{listing}
\subsection{CFRP}
\label{sec:cfrp}
Another RP language targeting embedded devices is
CFRP~\cite{suzuki_cfrp_embedded}. CFRP was created as a pure FRP language that
compiles to standalone C++ code. It was created to show that FRP is beneficial
for developing software for small-scale embedded devices.

It was designed as follows: a CFRP program consists of a series of declarations,
which denote signals and links to hardware (in C++), followed by a single
Haskell-like expression that builds the reactive
system~\cite{suzuki_cfrp_embedded}. The difference with EmFRP is that CFRP uses
a single expression to construct a dependency graph, which is then used to
compile to the C++ program. EmFRP uses nodes to construct the dependency graph.
Additionally, CFRP allows anonymous functions, whereas EmFRP drops them.
Moreover, CFRP has support for first-class signal types, whereas EmFRP does not.
These features do come with a cost, since EmFRP drops these features to keep its
memory use predictable~\cite{suzuki_cfrp_embedded}. The caveat with CFRP is that
the C++ code the program references has to be defined in separate C++
files~\cite{suzuki_cfrp_embedded}. This means that only the \enquote{global}
reactive system is defined in CFRP and the rest in C++.
\par
An example can be seen in~\cref{lst:example-program-in-cfrp}, where the air
conditioner is turned on or off depending on a discomfort index. The discomfort
index is calculated from the temperature \texttt{tmp} and humidity \texttt{hmd}.
CFRP uses \enquote{base} types that resemble C++ types, but signals have an
additional annotation \texttt{Signal}. Wrapping base types or tuples of base
types into a \texttt{Signal} type makes the size of signals predictable at
compile time~\cite{suzuki_cfrp_embedded}.
\begin{listing}[ht]
    \begin{lstlisting}[language=cfrp]
-- Including C++ header files
%{
#include "sensors.h"
#include "ac_ctrl.h"
%}

-- Declaring identifiers connected to external devices
%input tmp :: Signal Float = sen_tmp;
%input hmd :: Signal Float = sen_hmd;
%import ac :: Signal Bool -> Signal () = ctrl_ac;

-- Main expression
let di t h = t - 0.55 * (1 - 0.01 * h) * (t - 14.5) in
    ac (lift1 (\x -> x > 24) (lift2 di tmp hmd))\end{lstlisting}
    \caption{Example program in CFRP~\cite{suzuki_cfrp_embedded}}
    \label{lst:example-program-in-cfrp}
\end{listing}
\subsection{Haai + Remus}
\label{sec:haai-remus}
Haai is a pure RP language in which programs are composed of reactors and
deployments of reactors. We call Haai \enquote{pure} because everything is
reactive, even its primitives~\cite{oeyen2024reactive}. Additionally, Haai is an
independent language, meaning it does not rely on a host language, the way
REScala that relies on Scala~\cite{surveyRP2024}. Nowadays, Haai comes with a
virtual machine (VM) called Remus, which primarily allows Haai to run on the
bare metal~\cite{rpbaremetal2022,oeyen2024virtual}. Remus was later implemented
in Rust and with some modifications a prototype was created to run a Haai
program on an M5StickC~\cite{descheemaeker2023compilation}.

The benefit of Haai is that it provides platform independence through its
compilation step from Haai to Remus bytecode. All that is required is a Remus
bytecode interpreter for the target device, in the language of choice.
Additionally, Remus is well suited for constrained devices as all the memory a
well-behaved program requires is allocated up front, achieving a predictable
memory footprint~\cite{oeyen2024virtual}. Moreover, the Rust implementation of
Remus provides the necessary interfaces to interact with sensors and
actuators~\cite{descheemaeker2023compilation}, leaving interoperability as the
only hurdle of this language. Fortunately, as we will see
in~\cref{sec:revisiting-the-problem-statement}, this can be solved by
implementing Remus in a different low-level language that the chosen robotics
framework does support.

Having discussed EmFRP, CFRP and Haai, we can conclude that they all meet most
criteria, though not all. Unfortunately, EmFRP and CFRP are partially portable,
as they have to be recompiled each time for their target platform. Additionally,
CFRP does not give a bound in terms of memory usage. Haai, in contrast, is
compiled once and then can be run anywhere with a Remus VM. Additionally, the
access to the Haai language makes it practical to make necessary language
extensions, should they be required. Therefore, this thesis will build on Haai
and Remus.
\par
In this thesis we focus on a system of MCUs. Take a robot, for example: a robot
has sensors as input and has other peripherals that are then used to interact
with the real world, depending on these inputs. In other words, the robot reacts
to the sensors by instructing the motors what to do or where to move next.
\par
To build this system of embedded devices, we could create some reactive programs
in Haai, but this would leave the developer responsible for implementing all the
communication between the devices as well as some central computing unit that
coordinates all these devices and peripherals, most of the time requiring the
developer to use a library that uses some kind of communication protocol under
the hood (Bluetooth, UART, I2C, SPI, USB, etc\dots). A standardized toolkit that
abstracts these complexities away would be easier, which is what we will be
looking into next.
\section{Robotics frameworks}
\label{sec:robotics-frameworks}
In this section we will discuss robotics frameworks that are open source,
provide a software development kit (SDK) to aid development and have a user
base: Robot Operating System (ROS)~\cite{quigley2009ros, macenski2022robot,
allaban2021developing, belsare2023microros}, Open Robot Control Software
(OROCOS)~\cite{bruyninckx2001open} and Yet Another Robot Platform
(YARP)~\cite{metta2006yarp}. We will analyse each framework, see how it works,
if it runs on MCUs and whether it abstracts away the communication between
devices.
\subsection{ROS}
\label{sec:ros}
Originating from Stanford, Robot Operating System, or ROS, is in fact not
an operating system but rather an SDK~\cite{macenski2022robot}.
To clarify, when we speak of ROS, we refer to ROS 2, unless stated otherwise.
\subsubsection{Architecture}
ROS provides modules to aid in the development of robotics systems.
The modules can be categorized as follows~\cite{macenski2022robot}:
\begin{itemize}
	\item Middleware: the communication between components.
    \item Algorithms: libraries of commonly used algorithms.
    \item Developer tools: tools to configure, launch, inspect and debug
        ROS applications.
\end{itemize}
The middleware is essentially \enquote{a structured communications layer above
the host operating systems of a heterogenous compute
cluster}~\cite{quigley2009ros}. A ROS cluster consists of several on-board
devices and off-board devices, which can connect and disconnect at runtime.
Consequently, the designers of ROS chose a peer-to-peer (p2p) system as having a
central server would mean a lot more network saturation as messages would have
to go to a central point and would then have to be forwarded to their respective
recipients. In a p2p system, nodes communicate directly, without a central
system, leading to less network saturation and shorter distances
travelled~\cite{quigley2009ros}.
\par
The philosophy of ROS of using multiple standalone components within its system
allows for developers to reuse or repurpose existing hardware libraries within
ROS, but without actually depending on ROS. This also allows for robust testing
of these libraries, without being dependent on ROS. The decoupling of these
components also means that they can be used in other robotics systems where
there is no inherent dependency and vice versa, giving ROS access to existing
standalone components, such as drivers and vision algorithms~\cite{quigley2009ros}.
\subsubsection{Communication}
A ROS application consists of nodes, which are processes that perform a
computation. Multiple of these form a larger system that mimics the structure of
a graph. Note that a node is not necessarily mapped to one device, as a device
could run a single node or many. To communicate between these nodes, messages
are sent. To facilitate communication, ROS provides three abstractions to send
these messages: topics, services and actions~\cite{macenski2022robot}.

\Cref{fig:ros-node-graph-example} shows a robotics example where some products
are being transported down a conveyor belt. However, these products have to be
classified by colour, which the sensors on the \enquote{sensors} device can
detect. The sensors can then send the detected colour to the operator computer,
which selects the appropriate sorter to sort the product. Each sorter consists
of an arm and a sensor. The sensor detects when the product is in the sorting
range and sends a signal to the arm, which sorts it. Furthermore, the operator
computer shows the detected colours on the screen and allows the user to
manually operate a sorter if need be thus completing the graph shown in the
figure.

Messages that these nodes send to each other are actually strictly typed data
structures. These can consist of the ROS-provided primitive types (integer,
floating point, boolean, etc\dots), arrays of primitive types as well as
constants though they must be defined in a \texttt{.msg} file, an interface
definition language (IDL). An example can be seen in
\cref{lst:product-colour-msg}. Messages can also be composed of other messages
or arrays of messages which can be nested arbitrarily deep.
Do note that ROS automatically generates native types for the types used in the
IDL, depending on the language where ROS is used. For instance, if the node is
written in C++, ROS will (de)serialize to C++ types~\cite{quigley2009ros}. This
also counts for nodes running on Python or C, just like JSON is automatically
(de)serialized in other high-level programming languages. The ROS Client library
that provides the API to create a ROS graph is called rcl, which is written in
C. Depending on the language used, the API is built upon further resulting in
rclcpp (C++), or rclpy (Python).

	\centering
	\includegraphics[width=0.7\textwidth]{./images/ROS-nodes-example.drawio.pdf}
	\caption{ROS node graph example}
	\label{fig:ros-node-graph-example}
\end{figure}
\par
\begin{listing}[ht]
	\begin{lstlisting}
# ProductColour.msg
uint64 timestamp_ms
string colour\end{lstlisting}
	\caption{Message definition for a detected colour}
	\label{lst:product-colour-msg}
\end{listing}
\par
% TODO [medium]: source only says actions are built on topics AND services (ros2docs_actions); "topics are the main abstraction" doesn't follow from it.
Within ROS, topics are the main communication abstraction, as actions are built
on top of topics and services~\cite{ros2docs_actions}. A topic is essentially a
channel that allows nodes to publish or subscribe to the topic. This allows for
a many-to-many relationship within the ROS node graph. An illustration of
\cref{fig:ros-node-graph-example} implemented using topics can be seen in
\cref{fig:ros-nodes-example-improved}. Topics allow for unidirectional
one-to-one, one-to-many, many-to-many or many-to-one relationships. A
bidirectional relationship between two nodes can be created by making one of the
nodes a subscriber to a topic and the other a publisher as well as the inverse
on another topic as seen on the operator computer.
\par
\begin{figure}[ht]
    \centering
    \includegraphics[width=0.7\textwidth]{./images/ROS-nodes-example-improved1.drawio.pdf}
    \caption{ROS node graph with topics}
    \label{fig:ros-nodes-example-improved}
\end{figure}
Whilst topics are the main communication abstraction that ROS uses, they are
lacking for communication where a message sent expects a response. To solve
this, ROS provides services, which work analogously to web services. A node
places a request to a uniquely named service that sits on another node, which
returns a response after processing the request, just like web
services~\cite{quigley2009ros}. This is shown
in~\cref{fig:ros-service-procotol}.
\begin{figure}[ht]
    \centering
    \includegraphics[width=0.5\textwidth]{./images/ros-request-response-diagram.drawio.pdf}
    \caption{ROS service protocol}
    \label{fig:ros-service-procotol}
\end{figure}
\par
Like messages, the interface of services must be declared in an IDL. In this
case it will be in a \texttt{.srv} file instead of a \texttt{.msg} file, though
the same principle applies. The only difference is that the interface is split
in two. Above the \texttt{-{}-{}-} is the interface of the request and below the
interface of the response. An example can be seen in
\cref{lst:get-sorter-status-srv}, where we send a request to a node to get the
number of items a specific sorter has sorted. The sorter is identifiable by
\texttt{sorter\_id} and the response is \texttt{count}.
\begin{listing}[ht]
	\begin{lstlisting}
# SorterService.srv
uint32 sorter_id
---
uint32 count\end{lstlisting}
	\caption{Service definition for the count of a sorter}
	\label{lst:get-sorter-status-srv}
\end{listing}
\par
In case both topics and services are inadequate and you need the best of both
worlds, there are also actions. Actions are a combination of both topics and
services and ideal for long-running tasks and work as follows: an action starts
off like a service, a node sends a request to a uniquely named action, which in
turn has to process the request. During the processing of the request the
uniquely named action produces some feedback which gets published to a topic and
is sent to its subscribers. After processing the request a response is sent back
to the node that made the request. Unlike services or topics, actions allow for
cancellation of the request if needed. A diagram showing the flow of actions can
be seen in~\cref{fig:ros-actions-protocol}.
\begin{figure}[ht]
    \centering
    \includegraphics[width=0.8\textwidth]{./images/ros-actions-diagram.drawio.pdf}
    \caption{ROS actions protocol}
    \label{fig:ros-actions-protocol}
\end{figure}
\par
Like the interface of messages and services, the interface of actions must be
defined in an \texttt{.action} file. Like the interface of services, the
interface of actions is also split up but three-way instead of two-way. The
first segment declares the interface of the request. The second of the response
and the third segment declares the interface of the messages published to the
topic. An example can be seen in
\cref{lst:sort-batch-action}. In this example the operator computer tells a
specific sorter to sort a batch, whilst keeping track of the number of sorted
items so far, and finally receives the total count of sorted items.

---
uint32 sorted_total
---
uint32 sorted_so_far\end{lstlisting}

\subsubsection{History of ROS}
ROS 1 is the predecessor of ROS 2 as the number probably already suggested,
however they are vastly different. As ROS 1 started as a research platform and
as it grew in popularity across robotics, its limitations became increasingly
evident. \enquote{Security, reliability in nontraditional environments, and
support for large-scale embedded systems became
essential}~\cite{macenski2022robot}. Since ROS 1 did not provide solutions for
these concerns, developers were forced to create application-specific
workarounds~\cite{macenski2022robot}, which could not be reused. To solve these
issues, ROS was rebuilt from the ground up and thus ROS 2 was
born~\cite{macenski2022robot}. A summary of the comparison of features between
the versions can be seen in \cref{tab:ros1_vs_ros2}.

Without getting into too much of the technical changes, the most noteworthy
changes would be the new underlying network communication, the Data Distribution
Service (DDS), which is also used in critical
infrastructure~\cite{macenski2022robot}, peer-to-peer discovery and the support
for embedded systems.
\par
The change to DDS as its network communication solved many of the problems, as
DDS enables ROS 2 \enquote{to obtain best-in-class security, embedded and
real-time support, multirobot communication, and operations in nonideal
networking environments}~\cite{macenski2022robot}. DDS provides peer-to-peer
discovery, which is one of ROS 2's core defining features, as DDS is the
underlying medium that the communication abstractions depend on.
\subsubsection{MCU support}
Unlike ROS 1, which only had minimal experimental support through rosserial, ROS
2 supports embedded systems~\cite{macenski2022robot}. It does so because sensors
and actuators of a robot are often driven by MCUs, which are constrained in
memory and are unable to run a ROS system. Yet these MCUs are still expected to
communicate with a CPU running ROS~\cite{macenski2022robot}. ROS 2 supports MCUs
by providing a dedicated SDK called micro-ROS~\cite{belsare2023microros} for
resource-constrained devices (such as MCUs). The SDK provides all major features
that the ROS 2 SDK provides by reusing as many packages as possible and
providing them in C by extending the existing ROS client library (rcl), which is
written in C, with the rclc packages. Like rclcpp does for C++, together they
form a complete client library for C~\cite{belsare2023microros}.
\par
To be able to provide all these major features, micro-ROS replaces DDS with
XRCE-DDS, which is a variant of DDS for extremely resource-constrained
environments~\cite{omg2020ddsxrce}. An agent running on a CPU bridges between
XRCE-DDS and DDS, allowing MCUs to communicate with nodes running
ROS~\cite{belsare2023microros}.
\par
Unfortunately, micro-ROS cannot be used on every single microcontroller. As ROS
2 was initially developed for POSIX-based operating systems, some clock and
timing functions remain of the essence. This means that the microcontroller has
to either be able to run an RTOS providing these functions or have abstractions
providing them. Currently, micro-ROS supports some Real-Time Operating Systems,
such as FreeRTOS, Zephyr and NuttX, as well as some boards such as Espressif
ESP32, Raspberry Pi Pico, some Arduino boards and some STM
boards~\cite{belsare2023microros}. There is also experimental support for
bare-metal usage, other RTOSes and other boards. Boards contributed by the
community are not guaranteed to be supported, whereas officially supported
boards, such as the Raspberry Pi Pico, are tested and receive long-term
support~\cite{microros_hardware}.
\par
Whilst micro-ROS tries to provide as many of the features that ROS 2 provides,
there are some considerations that have been made, as the environment has
resource constraints, and thus cannot provide all
features~\cite{belsare2023microros}:
\begin{itemize}
	\item The messages interchanged between two nodes, including at least one
        micro-ROS node must be a fixed size. This is to avoid dynamic memory
        allocations, which is heavily discouraged to do on a microcontroller.
        This is because it is a best practice to allocate all the memory you
        need upon initialization, as running out of memory during runtime could
        yield undefined behaviour.
	\item To deal with different mechanisms and scheduling APIs of the
        underlying RTOS, rclc provides a flexible Executor on the level of
        individual callbacks.
	\item ROS 2 provides a launch system, which starts and configures many nodes
        with a single command~\cite{ros2docs_launch}. Micro-ROS does not have
        this due to different underlying RTOS mechanisms and leaves it up to the
        developer.
	\item Standard ROS 2 allows for dynamic loading of nodes into running
        processes. Since the program has to be flashed onto the microcontroller,
        the node composition of the micro-ROS program has to be known ahead of
        time, and thus at compile-time.
	\item The XRCE-DDS standard defines no security and thus relies on the
        mechanisms provided by the underlying transport medium. If the medium
        (e.g., UART) has no security, then the connection is not encrypted.
        Though for wired connections, this is generally considered acceptable.
\end{itemize}
To summarize, ROS is an SDK which provides modules to aid robotics development.
Most notable is its communication layer, which allows for peer-to-peer
communication. ROS also provides an SDK for development on microcontrollers,
though not all microcontrollers. ROS thus supports MCUs, provides common
libraries and handles the communication between devices for us.
\subsection{OROCOS}
\label{sec:orocos}
Open RObot COntrol Software (OROCOS) started at the Katholieke Universiteit
Leuven (KUL) as a project that \enquote{aims at becoming a general-purpose and
open robot control software package}~\cite{bruyninckx2001open}.
\subsubsection{Architecture}
OROCOS is a free software framework aimed at real-time control of robots and
machine tools~\cite{orocos_history}. Its toolchain is used to build real-time
software components and also takes care of the communication and execution
of and between these components~\cite{orocos_rtt_manual}.
A component can be seen as a unit of functionality
that runs one or more programs on a thread~\cite{orocos_rtt_manual}. OROCOS
consists of the following parts:
\begin{itemize}
	\item The OROCOS toolchain
        \par
        The OROCOS toolchain is composed of the Real-Time Toolkit (RTT), the
        OROCOS Component Library (OCL) and finally code generation tools for C++
        data types and ROS messages. The RTT can be seen as the middleware
        between the application and the operating system (OS). It abstracts the
        OS, runs the components, and handles communication between components.
        The OCL provides prebuilt components that are commonly used in an OROCOS
        system, logging components for example~\cite{orocos_rtt_manual}.
	\item Standalone libraries
        \par
        These are libraries that were created to be independent of the OROCOS
        toolchain. This means you are able to use them outside of an OROCOS
        project. The libraries are the Kinematics and Dynamics Library (KDL) and
        the Bayesian Filtering Library (BFL)~\cite{orocos_history}. KDL is used
        to compute positions and motions of joints and links of
        robots~\cite{orocos_kdl}. BFL is used to estimate the true state of a
        robot from noisy sensor data~\cite{orocos_bfl}.
	\item Integration and tooling
        \par
        This part is composed of integrations to interoperate with another
        robotics framework, interestingly, ROS~\cite{orocos_rtt_ros,
        orocos_rtt_ros2}, which is discussed in \cref{sec:ros}. OROCOS provides
        \texttt{rtt\_ros2\_integration} to interoperate OROCOS components with
        ROS nodes~\cite{orocos_rtt_ros2}. Additionally, this part consists of a
        tool to generate motions of robots from constraints
        (iTaSC)~\cite{orocos_itasc} and a tool to coordinate robots with state
        machines (rFSM)~\cite{orocos_rfsm}.
\end{itemize}
\subsubsection{Communication}
OROCOS offers abstractions to communicate between components. The abstractions
can be classified under the following two categories: data flow ports and
operations.
\par
Data flow ports can be seen as a many-to-many communication. Conceptually it can
be seen as publish-subscribe. Each component declares input ports
(\texttt{InputPort<T>}) and output ports (\texttt{OutputPort<T>}), where
\texttt{T} is the data type of the payload that is transmitted between ports;
this can be any C++ data type, struct or class, for example \texttt{double}.
Each \texttt{OutputPort<double>} can be connected to multiple
\texttt{InputPort<double>} of a different component, and multiple
\texttt{OutputPort<double>} can be connected to a single
\texttt{InputPort<double>}. The connection itself can be created outside the
component through a script or an XML file. The usual way these connections are
created is by using the deployer, an OCL component that runs the script or XML
file containing the connection declarations. However, you can also create the
connections in your own C++ program~\cite{orocos_rtt_manual}.
\par
Operations are essentially methods that are provided by components that can be
called by other components through an \texttt{OperationCaller}, which is a
helper object for calling operations~\cite{orocos_rtt_manual}. Conceptually,
this is similar to Remote Method Invocation (RMI). The component that wants to
provide the operation registers the method or function as an operation in its
interface. This makes the operation available to other components, and can be
done by using \texttt{addOperation} in the component's constructor. It registers
the operation under a name, with the associated function and component, and
declares where the function is meant to run: either in the component's own
thread (\texttt{OwnThread}) or in the caller's thread (\texttt{ClientThread}),
which often requires using a mutex to be thread safe. This can be seen in
\cref{lst:orocos-register-operation}. Other components can in turn fetch the
operation from the component and save it to an \texttt{OperationCaller} helper
with the same signature as the registered method. Once the component needs to
invoke the operation, this can be done synchronously by calling the method like
you would call a function, or asynchronously by calling \texttt{send()} on the
\texttt{OperationCaller}, which returns a \texttt{SendHandle}. The result can
later be collected by using \texttt{collect()} or \texttt{collectIfDone()} on
the handle, as seen in
\cref{lst:orocos-call-send-operation}~\cite{orocos_rtt_manual}.
\begin{listing}[ht]
	\begin{lstlisting}[language=C++, morekeywords={[2]TaskContext,OperationCaller,SendHandle,SendStatus,OwnThread,ClientThread}]
class Sorter : public RTT::TaskContext {
public:
    uint32_t sorted_items = 0;

    void operate(){
        // logic to sort
        this->sorted_items++;
    }

    uint32_t getSortedCount(){ return this->sorted_items; }

    Sorter(std::string name): TaskContext(name) {
        this->addOperation("operate", &Sorter::operate, this, RTT::OwnThread);
        this->addOperation(
            "getSortedCount",
            &Sorter::getSortedCount,
            this, RTT::OwnThread);
    }
};
\end{lstlisting}
	\caption{Registering methods as operations in OROCOS}
	\label{lst:orocos-register-operation}
\end{listing}
\par
\begin{listing}[ht]
	\begin{lstlisting}[language=C++, morekeywords={[2]TaskContext,OperationCaller,SendHandle,SendStatus,OwnThread,ClientThread}]
    TaskContext* sorter = getPeer("sorter");
    OperationCaller<uint32_t(void)> getSortedCount = sorter->getOperation("getSortedCount");

    uint32_t count = getSortedCount(); // synchronous call

    SendHandle<uint32_t(void)> handle = getSortedCount.send(); // asynchronous call

    while (handle.collectIfDone(count) == SendNotReady){
        // do work whilst getSortedCount runs asynchronously
    }

    handle.collect(count); // Alternative way to collect async result but blocking
\end{lstlisting}
	\caption{Fetching an operation and calling or sending it in OROCOS}
	\label{lst:orocos-call-send-operation}
\end{listing}
\par
Under these abstractions OROCOS makes use of transports, which are a layer that
carries ports and operations from one process to another. The first transport is
CORBA, which is used between processes and across the network. This allows
components to live in separate processes or even devices and still be able to
communicate with each other. It works for both ports and
operations~\cite{orocos_rtt_manual}.
\par
The second transport is called MQueue. MQueue allows for real-time communication
between processes on the same device, as it uses POSIX message queueing
available on Linux systems. This transport is limited to
ports~\cite{orocos_rtt_manual}.

Additionally, OROCOS can make use of most of ROS's communication abstractions
through its ROS integration library~\cite{orocos_rtt_ros, orocos_rtt_ros2}.
\subsubsection{History of OROCOS}
Before OROCOS, most of the robotics software was closed source and did not allow
developers to go into the deepest layers of hardware
control~\cite{bruyninckx2001open, orocos_history}. This led to disappointing
experiences for Herman Bruyninckx, who came up with the idea for
OROCOS~\cite{orocos_history}.
\par
Originally, the plan was to split OROCOS into three parts: supporting modules,
robotics modules and components~\cite{bruyninckx2001open}. Supporting modules
would come from neighbouring projects whilst the robotics modules would be a
% TODO [medium]: orocos_history doesn't say "today the robotics modules are KDL and BFL"; it calls them stand-alone libraries ("robotics modules" is from bruyninckx2001open).
collection of commonly used algorithms~\cite{bruyninckx2001open}. Today the
robotics modules are the KDL and BFL libraries~\cite{orocos_history}. Components
were originally CORBA objects which were built from the other two types of
modules. Developers could use these objects to create their robot control
software~\cite{bruyninckx2001open}. Nowadays components are built using
\texttt{TaskContext} from the RTT and CORBA is used as a means of
transport~\cite{orocos_rtt_manual}.
\par
As of November 2026, the repositories containing the source code of OROCOS show
that only KDL is actively maintained and the others have had their last
maintenance during 2020--2022~\cite{orocos_kdl_repo, orocos_rtt_repo,
orocos_ocl_repo, orocos_bfl_repo}. OROCOS wants to provide the best open source
software within its niche. It provides KDL and BFL as standalone libraries and
allows other frameworks to use them~\cite{orocos_history}. This leads to OROCOS
often not adopting extensions and features into the project but instead
delegating them to neighbouring projects such as ROS, which is in line with
OROCOS providing the integration library with ROS~\cite{orocos_history,
orocos_rtt_ros, orocos_rtt_ros2}.
\subsubsection{MCU support}
Originally, OROCOS was designed so that it could even run without an

OS~\cite{bruyninckx2003realtime}. However, the implementation only ever targeted
Linux and variants of Linux~\cite{bruyninckx2003realtime, orocos_rtt_manual}. In
principle, it should be possible to port it as long as you can use an RTOS with
full C++ support, as you need time reading, mutexes, semaphores and condition
variables~\cite{orocos_rtt_manual}. Such a port, to our knowledge, does not
exist. Although the manual mentions that OROCOS can be used on embedded devices
with less than 1 MB of memory~\cite{orocos_rtt_manual}, this refers to the
smallest deployment on a Linux target. Additionally, the transport layers assume
a full OS, as they rely on POSIX message queues, an ORB and a naming service,
and OROCOS does not provide a lightweight alternative for
microcontrollers~\cite{orocos_rtt_manual}. This means that OROCOS is inadequate
for building a distributed system of microcontrollers, as it has yet to prove
that it can run on microcontrollers. However, it could be used as a supporting
tool within a different robotics framework, just as KDL is used within
ROS~\cite{orocos_history}.
\subsection{YARP}
\label{sec:yarp}
Yet Another Robot Platform or YARP, developed at the LIRA-Lab and MIT, was
created for the application of humanoid robotics, with a focus on applications
that are real-time, computation-intensive and involve interfacing with diverse
and changing hardware~\cite{metta2006yarp}. YARP categorizes itself as a
middleware for robotics~\cite{fitzpatrick2014middle}. It is a set of libraries,
protocols, and tools to keep modules and devices
decoupled~\cite{yarp_docs_what}. The goal of YARP is \enquote{to minimize the
effort devoted to infrastructure-level software development by facilitating code
reuse, modularity and so maximize research-level development and
collaboration}~\cite{metta2006yarp}.
\subsubsection{Architecture}
The architecture of YARP can be split into three parts: the OS, signal and
device libraries~\cite{yarp_docs_what}.
\begin{itemize}
    \item OS library (\texttt{YARP\_os})
        \par
        Just as the RTT is the core of OROCOS, \texttt{YARP\_os} is the core of
        YARP. It provides an OS layer abstraction so YARP can remain OS
        independent~\cite{yarp_docs_what}. It also contains the communication
        abstractions, which are described in the Communication part below.
    \item Signal library (\texttt{YARP\_sig})
        \par
        Since humanoid robots often require vision and use cameras to see, or
        microphones to hear, libraries to process these signals are mandatory
        for YARP~\cite{metta2006yarp}. It supports images, audio, vector and
        matrix data as well as 3D point clouds (points that describe the surface
        of an object) and measurements from lasers. Interestingly, most of these
        data types implement YARP's \texttt{Portable} interface, meaning they
        are serializable out of the box~\cite{yarp_repo}.
    \item Device library (\texttt{YARP\_dev})
        \par
        The device library offers interfaces for common devices used in robotics
        as well as drivers implementing those interfaces for concrete
        devices~\cite{yarp_docs_what, yarp_docs_devices}. Moreover, since some
        devices also rely on network communication, YARP wants a scalable way to
        communicate across devices. To solve this, the library offers network
        wrappers so devices have a common interface with which they can
        communicate~\cite{yarp_docs_devices, yarp_docs_nws}. This makes
        communication device- and location-agnostic.
\end{itemize}
\subsubsection{Communication}
\label{sec:yarp-communication}
YARP processes communicate with each other by making use of the Observer pattern
and port objects. Port objects are active objects that manage multiple
connections. Each connection has a state that can be manipulated from external
commands, which manage the connection or obtain state information from it. Ports
can either be declared as an input, or as an output. An input port can receive
from many connections over different protocols. An output port can send to many
receivers~\cite{metta2006yarp}. All ports get a unique readable name and are
kept track of in the name server. The name server returns the address of the
associated port when looked up by name. After this, communication goes straight
to that address~\cite{metta2006yarp, yarp_docs_terms}.
\par
Underneath port objects, YARP uses low-level protocols to communicate, called
carriers. YARP provides the following carriers~\cite{metta2006yarp,
yarp_docs_terms}:
\begin{itemize}
	\item TCP, a reliable protocol. TCP guarantees
	      delivery.
	\item UDP, a faster protocol than TCP, but without a delivery guarantee.
	\item Multicast, used for one-to-many connections. This is efficient when
        wanting to share the same information across many processes.
	\item Shared memory. This is used for local connections when possible.
	\item QNet, a fast and synchronous protocol, used under the QNX real-time
        OS.
\end{itemize}
\par
YARP provides serialization for all simple data types (i.e., not containing
pointers) out of the box. More complex data types using pointers must first have
their pointers recursively dereferenced and require appropriate
(de)serialization functions~\cite{metta2006yarp}.
\par
YARP also provides Remote Procedure Call (RPC) ports to communicate between
processes, which are an additional layer on top of ports. The difference lies in
how they handle
% TODO [low]: yarp_docs_rpc only says "a message and a reply" vs streaming "without replies"; synchronous/waiting is from the example code.
sends and receives. Regular ports are asynchronous, meaning that the sender does
not wait for the receiver to process anything. RPC ports are synchronous because
they actually wait for the receiver to send a response~\cite{yarp_docs_rpc}.
\par
Like OROCOS, YARP also provides interoperability with ROS 2, though it does not
allow communication between ports and ROS 2 nodes like OROCOS
does~\cite{orocos_rtt_ros2}. Instead, YARP provides wrappers for devices in its
device library to interoperate with ROS 2 called
\texttt{yarp-devices-ros2}~\cite{yarp_devices_ros2, yarp_docs_nws}. This allows
these devices to become ROS 2 nodes with fixed topics or services.
\par

\subsubsection{History of YARP}
Humanoid robots need a lot of computing power. The only realistic way to achieve
this is by having a cluster of computers. YARP's design revolves around how the
processes on these computers can communicate with each other as easily as
possible. Over the years the developers of YARP have learned the following
lessons that make YARP what it is today~\cite{metta2006yarp}:
\begin{itemize}
	\item A robot control system consists of multiple processes. This means that
        the developer must be able to design the system as a set of processes
        running on a set of computers. This maximizes the amount of time spent
        researching instead of optimizing code. Consequently, writing and
        running processes has to be as easy as possible.
	\item Whenever a single process has a single responsibility, it can be
        reused on any computer without code changes and can be moved during run
        time to spread the computational load or to recover from a hardware
        failure.
	\item Since the actual performance of a robot controller depends on the
        timing of various signals, existing processes should feel minimal
        interference when another process is created within the system.
	\item Since some processes could depend on other processes, it would be
        ideal to minimize these dependencies to prevent expensive chains or
        process restarts.
	\item YARP is meant to be used alongside external libraries that themselves
        do not necessarily depend on YARP. YARP does not try to be in control of
        the project and instead aims to support the project by allowing the
        developer to only use parts of YARP it needs.
    \item YARP is designed to be OS independent. Sometimes some tools are better
        in one OS rather than another. YARP uses an open source library that
        provides a concurrent framework across a wide variety of operating
        systems~\cite{metta2006yarp}.
\end{itemize}
\par
During the ROS 1 era, YARP was able to communicate directly with ROS 1 through
nodes and the publish-subscribe architecture~\cite{fitzpatrick2014middle}.
However, since YARP 4.0, it has dropped support for ROS 1 in favour of the
device wrappers that support ROS 2~\cite{yarp_release_v4, yarp_devices_ros},
which are still being maintained~\cite{yarp_devices_ros2}.
\subsubsection{MCU support}
YARP officially supports Ubuntu 22.04, Windows 10 and macOS
12/13~\cite{yarp_repo}, and it has also been used on iOS, Solaris and Android as
well~\cite{yarp_docs_what}. These are all OSes, meaning YARP has to run on a
device that at the very minimum runs one of the mentioned OSes. This implies
that like OROCOS it is short of supporting microcontrollers, as they often do
not have the resources to run such a heavy OS. However, YARP can interact with
microcontrollers as it has with iCub, a robot YARP was used
for~\cite{randazzo2018yarp}. iCub allows interoperability with MCUs by providing
drivers from which the computer can steer the MCUs~\cite{metta2006yarp,
yarp_docs_what}. Despite YARP being able to instruct MCUs through these drivers,
MCUs require firmware outside of YARP~\cite{icub_firmware}. This means that YARP
is also inadequate for the microcontrollers requirement.
\section{Revisiting the Problem Statement}
\label{sec:revisiting-the-problem-statement}
At the end of \cref{sec:rp-languages-targeting-mcus}, a reactive language that targets
MCUs was chosen: Haai with the support of Remus. This came with the caveat that
a Remus implementation would have to be made if the language of the
chosen robotics framework differs from existing Remus implementations. Afterwards, three
robotics frameworks were discussed in \cref{sec:robotics-frameworks}, namely ROS, OROCOS and YARP. Since OROCOS
and YARP are inadequate for microcontrollers, ROS is the only remaining choice,
as it provides support for microcontrollers through micro-ROS.
\par
Reusing the product sum example in \cref{fig:dependency-graph-product-sum},
suppose this program is distributed across three devices, two reading the inputs \texttt{x} and \texttt{y}
respectively. These devices communicate their values to a third device that
performs the product and sum. Using RP alone, three separate
programs would have to be made to be distributed and deployed on these different devices.
Additionally, the communication layer would have to be written, which also depends on the
medium used. This is called \textit{distributed reactivity}~\cite{surveyRP2024} and leads to reactivity
within the devices, but the glue between the devices hides the dependencies in
the communication code, making the data flow no longer explicit.
\par
ROS takes care of the communication code and allows programs to be structured in
a node system. For instance, a signal can be rewritten as a ROS node and the
dependencies can be written as topics. Each signal that depends on another signal
subscribes to the topics of the signals it depends on. As an example, the Haai program from
\cref{lst:reactive-product-um} can be rewritten into a ROS system, split by nodes and
topics as shown in \cref{fig:haai-product-sum-to-ros}.
The two input devices publish their \texttt{x} and \texttt{y} inputs to topics, to which the
product sum device is subscribed. The product sum device computes the product
sum and further propagates it in the system. The downside is that this would
have to be created using callbacks, which brings back the problems discussed in
\cref{sec:reactive-programming}. This has not changed with ROS 2, although there
have been efforts to bring RP to ROS 2 through RxROS~\cite{Larsen2021}.
\begin{figure}[ht]
	\centering
	\includegraphics[width=\linewidth]{./images/haai-product-sum-in-ros.drawio.pdf} % Replace with your image file
	\caption{Product sum in a ROS node system}
	\label{fig:haai-product-sum-to-ros}
\end{figure}
\par
Despite RxROS allowing RP in a ROS system, the programs would still have to be
written independently of each other~\cite{Larsen2021}, which is a problem this thesis attempts to
solve by creating a distributed reactive program from a single source. Additionally,
RxROS is not supported in micro-ROS due to RxROS being implemented in
C++/Python whilst micro-ROS only provides support in C, which limits its usability~\cite{Larsen2021, belsare2023microros}.
\par
Since micro-ROS only supports C, and existing Remus implementations are in Rust
or Racket~\cite{descheemaeker2023compilation, oeyen2026personal}, the first contribution
of this thesis is a C port of Remus (\cref{ch:mu-remus}) so the bytecode of Haai can be run on
MCUs. This solves running micro-ROS nodes. However, since ROS 2 is not restricted
to C, there is more freedom in deciding how the ROS 2 parts of the program are
run. A solution could be to reuse the C implementation of Remus, resulting in a
single implementation for all devices. Alternatively, the existing Racket
implementation could be used through a foreign function interface (FFI) to rcl.
\par
Despite these solutions, separate reactive programs would still have to be
created, deployed and glued together by hand. Tierless programming addresses this.

\section{Tierless Programming}
\label{sec:tierless-programming}
Right now we have compared some RP languages, more specifically, some that run
on microcontrollers. We have compared some robotics frameworks, whose goal is to
aid in robotics development. However, robotics systems are often distributed,
some parts are responsible for sensing the environment, some are responsible for
reacting to it, with others responsible for everything in between. This would
mean that we have to create different RP programs, and somehow connect them as
they are deployed. This seems rather inefficient, and to elaborate further we
would like to introduce the concept of tierless programming or multitier
programming~\cite{weisenburger2020survey}.
\par
The goal is simple. We have different parts of a program that live separate on
different computers yet are coupled by a network. In traditional tierless
systems, such as a web environment, a developer would have to not only develop
client side code as well server side code, but also code glueing these tiers
together. This gives the illusion that these tiers are decoupled from each other
while in actuality they work closely together and actually also depend on each
other. To avoid writing extra glue code or huge API boilerplates we could
instead unify these tiers into a single source language.
\par
Writing a tierless program in a single source language not only saves the
developer from writing a lot of boilerplate code or glue code, it also abstracts
away the low-level details relevant to the distributed program. This allows the
developer to focus purely on the high level interactions and not worry about
error-prone aspects like network communication. Additionally, it saves the
developer from having to design inter-tier APIs, as the program is already
inherently intertwined in the source file. How the tiers are connected becomes a
compilation step rather than a development step.
\par
In traditional distributed programming, the boundaries between hosts or
functionalities may not always coincide. Meaning a single functionality may be
distributed across many places and many functionalities could be isolated to a
single place. Whenever functionalities are split across different devices,
changing them could become cumbersome as the same functionality is implemented
multiple times. Using tierless programming would allow the developer to
implement it once and distribute it where it is needed. Furthermore, an update
to the said functionality would also update all the functionalities that are
distributed in the system.
\par
Reasoning about a distributed system is complex. You could visualize a
distributed system as a graph, where the edges between the nodes would show
inter-tier communication. These edges could show that the system has a series of
one-to-one, one-to-many or many-to-many relationships. Reasoning about all these
different codebases or systems could become cumbersome as the edges increase and
thus also the complexity.
With tierless programming, you would not have to context switch between these
systems or codebases as the entire system or components that compose the system
are declared in a single source. The same goes for code comprehension. It is a
lot easier when everything is grouped together instead of scattered.
\par
Tierless programming languages can be categorized under the following
categories:
\begin{itemize}
	\item Degrees of tierless programming
	\item Placement strategy
	\item Placement specification \& granularity
	\item Communication abstractions
	\item Supported topologies.
\end{itemize}
\subsubsection{Degree of multitier programming}
Tierless programming languages either provide support for explicit placement of
distribution by means of for example an annotation such as \texttt{@server} or
\texttt{@client}, or they split code automatically by means of static analysis.
Alternatively, some tierless languages translate code across target platforms
(eg: Java to JavaScript).
\subsubsection{Placement strategy}
The placement strategy is the strategy adopted by the tierless language to split
the program up. A Tierless program can be partitioned into different
programs (statically or dynamically). Another option would be to separate the
program into different stages, where the execution of one stage generates the
next stage and can inject values computed in the current stage into the next.
\subsubsection{Placement specification \& Granularity}
The tierless languages that allow for explicit placement, can optionally also
allow varying degrees in granularity of the placement. Some tierless languages
could for example only allow complete blocks to be placed together on a tier
whilst other languages allow local bindings to be placed on different tiers.
\subsubsection{Communication abstractions}
Tierless languages also differ on the underlying communication used, so could
one language use Remote Procedure Calls (RPC), asynchronous callbacks,
directional message-passing channels, pub-sub mechanisms, distributed shared
state or even FRP streams.
\subsubsection{Supported topologies}
Another categorizing property of tierless programming is their supported
topologies. Most web-oriented tierless languages focus on the client-server
architecture. This means that most of the time they're exclusively meant for
that architecture, and sometimes also allow integration of a database. Some
tierless languages allow specification of tiers, such as
ScalaLoci~\cite{weisenburger2018scalaloci}.
\par
\begin{listing}[ht]
	\begin{lstlisting}[language=ScalaLoci]
@multitier object Chat {
     @peer type Server <: { type Tie <: Multiple[Client] }
     @peer type Client <: { type Tie <: Single[Server] }

     val message = on[Client] { Evt[String] }

     val publicMessage = on[Server] {
         message.asLocalFromAllSeq map { case (_, message) => message }
     }

     def main() on[Client] {
         publicMessage.asLocal observe println
         for (line <- io.Source.stdin.getLines)
            message.fire(line)
     }
}\end{lstlisting}
	\caption{Tierless program example from the ScalaLoci tutorial}
	\label{lst:scalaloci-example}

\end{listing}
To give an example how such a tierless program is written, consider the
following example in ScalaLoci defined in \cref{lst:scalaloci-example}.
It consists of a server and multiple clients where message events are sent to
the server, who then makes clients print it to their consoles. By using
\texttt{@peer} annotations we can define the structure of the tierless program.
We can define whether there is multiple of a tier or if there is a single one,
like multiple clients and a single server in this case. The cross-tier
boundaries are generated by the compiler as needed.
